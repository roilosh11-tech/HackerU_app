# מוח הקורס — פריסה ל‑Railway

אפליקציית לימוד כיתתית עם התחברות, פרופיל אישי לכל תלמיד, שמירת התקדמות והערות, גיימיפיקציה, ולוח מנהל/ת.

- **Frontend** — קבצי `*.dc.html` (Login / Course Brain / Admin) + `api.js` + `course-data.js` + `assets/`.
- **Backend** — FastAPI (`backend/main.py`), SQLite, מגיש גם את הפרונט וגם את ה‑API מאותו שרת.

הפרונט עובד בשני מצבים אוטומטית: **online** (יש שרת → התחברות אמיתית + שמירה בענן) ו‑**offline** (אין שרת, למשל תצוגה מקדימה → נשמר מקומית בדפדפן).

---

## הרצה מקומית

```bash
pip install -r requirements.txt
export ADMIN_USERNAME=admin
export ADMIN_PASSWORD=בחר-סיסמה-חזקה
export JWT_SECRET=מחרוזת-אקראית-ארוכה
uvicorn backend.main:app --reload --port 8000
```

פותחים http://localhost:8000 — מגיעים למסך ההתחברות. מתחברים עם פרטי ה‑admin שהגדרת.

---

## פריסה ל‑Railway

1. העלה את הפרויקט ל‑GitHub (או `railway up` דרך ה‑CLI).
2. ב‑Railway: **New Project → Deploy from GitHub repo**. Nixpacks יזהה Python אוטומטית (`requirements.txt` + `railway.json`).
3. **Variables** — הגדר:
   - `ADMIN_USERNAME` — שם המשתמש שלך (מנהל/ת)
   - `ADMIN_PASSWORD` — סיסמת המנהל/ת (חובה! בלי זה לא נוצר חשבון admin)
   - `JWT_SECRET` — מחרוזת אקראית ארוכה (למשל פלט של `openssl rand -hex 32`)
   - `DB_PATH` — `/data/course.db`
   - `ALLOW_SIGNUP` — `1` כדי לאפשר הרשמה (ברירת מחדל), `0` כדי לסגור
4. **Volume** — צרף Volume ומחבר אותו ל‑mount path **`/data`**. קריטי: בלי Volume מסד הנתונים נמחק בכל דיפלוי.
5. Deploy. הכתובת הציבורית של Railway היא הקישור שמשתפים עם הכיתה.

## זרימת המשתמש

- **תלמיד/ה** נכנס/ת ל‑`הרשמה`, יוצר/ת חשבון → מצב **ממתין לאישור**.
- **את/ה (admin)** נכנס/ת ל‑`Admin.dc.html` (מופיע כקישור בסרגל הצד רק לחשבון admin) → מאשר/ת או דוחה בקשות, ורואה את התקדמות כל הכיתה.
- לאחר אישור, התלמיד/ה מתחבר/ת ומקבל/ת גישה מלאה. כל ההתקדמות, ההערות, הכרטיסיות, הנקודות וההישגים נשמרים אוטומטית לפי משתמש.

## מה נשמר לכל משתמש
התקדמות וסטטוס לכל שיעור · הערות אישיות · מצב הכרטיסיות (חזרה מרווחת) · פריטים מוצמדים · נקודות · רצף ימים · הישגים · אחוז השלמת הקורס.

## תוכן הקורס משותף
השיעורים, המצגות והתובנות (`course-data.js`) זהים לכולם — רק ההתקדמות והמידע האישי נפרדים לכל תלמיד/ה.

## גלריית הפרויקטים (מרחב משותף לכל הכיתה)
במסך הבית — פיד משותף שבו כל תלמיד/ה מפרסם/ת פרויקט (כותרת + תיאור + קישור אופציונלי), נותן/ת „כל הכבוד” 👏 ומגיב/ה. **המידע נשמר בשרת ומשותף בין כל התלמידים** (לא מקומי לדפדפן), בטבלאות `posts` ו‑`post_comments` באותו מסד SQLite שב‑Volume `/data`. הרשאות: כל אחד מוחק את הפוסטים/התגובות של עצמו, ו‑admin מוחק הכל. ה‑endpoints:
`GET/POST /api/gallery` · `DELETE /api/gallery/{id}` · `POST /api/gallery/{id}/kudos` · `POST /api/gallery/{id}/comments` · `DELETE /api/gallery/{id}/comments/{cid}`. בתצוגה המקדימה (ללא שרת) הגלריה נופלת אוטומטית ל‑localStorage עם פוסטי דוגמה, כדי שהדמו יעבוד.

## תחזוקה — עדכון מסמכים ותוכן

### עדכון ספר מיישם AI (רילי מעדכנת כל שיעור)
פשוט מחליפים את הקובץ ב‑GitHub באותו שם ומבצעים commit:
```
assets/docs/ai-implementer-book.pdf
```
האפליקציה טוענת אותו אוטומטית — אין צורך לגעת בקוד. (מדריך הפרומפטים: `assets/docs/prompt-guide.pdf`.)

### מצגות השיעורים (PDF)
כל שיעור מציג את המצגת המקורית מקובץ בשם `lesson-N.pdf` (N = מספר השיעור) **בשורש ה‑repo** (לצד `course-data.js`, `api.js` וכו׳). להחלפה/הוספה — מעלים קובץ בשם הזה לשורש ה‑repo ב‑GitHub ומבצעים commit. הקבצים כבדים יחסית (~6–12MB כל אחד), לכן:
- **מומלץ:** GitHub Desktop (גרירה + commit + push, בלי הגבלות).
- דרך האתר: להעלות ב‑batchים קטנים (3–4 קבצים בכל פעם), לא הכול ביחד.

> הערה: המסלול של המצגות מוגדר בשדה `deck.file` של כל שיעור ב‑`course-data.js` (כרגע `'lesson-N.pdf'`). אם בעתיד תרצה לסדר אותן בתיקייה — העבר את הקבצים ל‑`assets/slides/` ועדכן את `deck.file` ל‑`'assets/slides/lesson-N.pdf'`.

### הוספת/עריכת תוכן שיעור
כל התוכן (שיעורים, פרקים, מושגים, ציטוטים, סיכומים, תובנות, כרטיסיות, `deck`) יושב ב‑`course-data.js` — עורכים שם, זה המקור היחיד לשני המסכים. מבנה שיעור: `num, date, title, duration, hook, status, chapters[], concepts[], quotes[], summary{}, deck{ file, totalSlides, coreConcepts[], gaps[] }`.

### אחרי כל שינוי
commit ל‑GitHub → Railway מפרסם אוטומטית → רענון קשיח בדפדפן (Cmd/Ctrl+Shift+R).

## קיבולת — כמה משתמשים זה מחזיק?
32 תלמידים זה עומס **קטן מאוד**. האפליקציה לא תקרוס מכמות המשתמשים:
- למידה מתפזרת על פני הזמן — גם לפני מבחן, רק בודדים לוחצים באותו רגע ממש.
- כל שמירה היא בלוק JSON קטן, ועם השהיה (debounce ~0.7 שניות) כדי לא להציף את השרת. SQLite במצב WAL מטפל בזה בקלות.
- מסלול ה‑$5 של Railway מספיק בשפע. אין צורך בסקיילינג, load balancer או מופע שני.

**הדבר היחיד שחשוב באמת לקיבולת/יציבות:** ה‑**Volume ב‑`/data`** (סעיף הפריסה) — הוא מה ששומר שהמידע לא נמחק בדיפלוי. זה, ולא מספר המשתמשים, הוא מה שיכול "לשבור" דברים.

## הצ׳אט "שאל את הקורס" (AI) — דורש מפתח
תכונת הצ׳אט משתמשת ב‑Claude. **בתצוגה המקדימה** היא עובדת דרך הסביבה המובנית; **בפריסה אמיתית ל‑Railway** אין את זה, ולכן הצ׳אט יציג הודעת "לא זמין" עד שיחובר מפתח API.

- כל שאר האפליקציה (שיעורים, סיכומים, הערות, המחברת, התקדמות, כרטיסיות, פרופילים, לוח מנהל/ת) עובדת **במלואה** בלי זה.
- כדי להפעיל את הצ׳אט בפריסה צריך: מפתח Claude API (מ‑console.anthropic.com), נקודת קצה קטנה בבקאנד שקוראת ל‑API עם המפתח (כמשתנה סביבה, לא בקוד הפרונט), והפניית הצ׳אט אליה. אפשר להוסיף בהמשך — לא חוסם את ההשקה.

## רעיונות לעתיד (Roadmap)
כיוונים לשיפור האפליקציה עבור הכיתה. הערה חשובה: תוכן שהתלמידים יוצרים (פוסטים, הגשות אתגרים) הוא **שלהם** — אין בעיית זכויות יוצרים כמו בתוכן השיעורים, אז זה החלק שאפשר להרחיב בחופשיות.

### 1. אתגרים שבועיים (הרחבה של הגיימיפיקציה הקיימת)
בונה על הנקודות/ההישגים/הרצף שכבר קיימים.
- **אתגרים במעקב אוטומטי** (קל, בלי מודרציה): למשל "השבוע: כבוש את הכרטיסיות של שיעור 5" או "חזור על 30 כרטיסיות". האפליקציה כבר יודעת חזרות/שליטה → מסמנת אוטומטית ומעניקה נקודות בונוס + תג שבועי.
- **אתגרים מבוססי-הגשה** (דורשים את המרחב המשותף): "בנה Artifact עם MoSCoW ופרסם אותו".
- המנהל/ת מפרסם/ת את האתגר מלוח הניהול; מוצג ב‑Home עם ספירה לאחור.
- **טבלת מובילים שבועית** ("הכי פעילים השבוע") — עדיף שבועי ומבוסס-פעילות ולא דירוג כל-הזמנים, כדי לעודד בלי לבייש מי שמפגר.

### 2. מרחב משותף (הערך הגבוה, שדרוג ארכיטקטוני)
היום כל המידע הוא **פר-משתמש**; פיד הוא מידע **משותף** — דורש נקודות קצה חדשות בבקאנד (יצירה/רשימה/מחיקה של פוסטים, תגובות, ריאקשנים), **מודרציה** (מנהל/ת יכול/ה למחוק הכול), ואם רוצים צילומי מסך — העלאת/אחסון תמונות. ל‑32 איש זה נוח לניהול, פשוט יותר מ‑tweak קטן. גרסאות מהקלה לעשירה:
- **גלריית פרויקטים** (מומלץ להתחיל מכאן): כל תלמיד/ה מפרסם/ת את פרויקט הקורס — כותרת, תיאור קצר, צילום מסך, לינק אופציונלי. בדיוק מה שקורס מבוסס-פרויקטים מייצר, ומאוד מניע לראות עבודות של חברים.
- **פיד רעיונות/שאלות**: פוסטים + תגובות + ריאקשן "כל הכבוד".
- **שו״ת פר-שיעור**: שאלה מוצמדת לשיעור ספציפי; חברים עונים. ערך גבוה, שומר על סדר לפי תוכן.

### סדר מומלץ למימוש
1. **קודם להשיק את מה שיש** (לסיים את הפריסה, לתת לאנשים להשתמש).
2. **אתגרים שבועיים** — קטן, בונה על הגיימיפיקציה הקיימת, בוסט מיידי למעורבות.
3. **מרחב משותף** — להתחיל צר עם **גלריית הפרויקטים** (הכי הרבה ערך, הכי מעט דרמה).

### רעיונות נוספים לבדיקה
- קבוצות לימוד / שותפי אחריות (accountability partners).
- "הנקודה הכי מבלבלת" פר-שיעור (אנונימי) → פידבק לרילי.
- דיג׳סט שבועי / מה מחכה לחזרה.
- ריאקשנים/כל-הכבוד על תובנות.
